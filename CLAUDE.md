# CardStock

Native macOS (26+) SwiftUI app: a front-end editor for flat-file blog/portfolio sites. Sites live in GitHub repos and are hosted by Cloudflare Pages (auto-deploy on push). Public repo, licensed under PolyForm Noncommercial 1.0.0 with an added permission to make any website (see LICENSE; versions before 0.4.0 were MIT).

## Workflow
- All coding is done from Claude Code; Xcode only builds in the background.
- The Xcode project is generated by XcodeGen from `project.yml`. Never hand-edit or commit `CardStock.xcodeproj`. New Swift files under `CardStock/` are picked up automatically on the next `xcodegen generate`.
- `scripts/build.sh` builds Debug and launches the app for preview. `--no-open` builds without launching.
- `scripts/test.sh` runs the unit tests (Swift Testing, `CardStockTests/`). CI runs them on every push.
- `scripts/make-dmg.sh [version]` builds Release into `dist/CardStock-<version>.dmg`.
- Scripts set `DEVELOPER_DIR` to /Applications/Xcode.app, so `xcode-select` doesn't need changing.

## Releases
- Bump `MARKETING_VERSION` in `project.yml`, commit, then tag `vX.Y.Z` and push the tag. `.github/workflows/release.yml` builds the DMG and creates the GitHub Release in this repo, with the tagged commit's message (minus the co-author line) as the notes, so write release commit messages for readers, and put HTML like `<!-- section -->` in backticks.
- Builds are ad-hoc signed (not notarized) until a Developer ID is set up.

## Code layout
- `CardStock/App`: app entry point, `AppModel` (open site, selection, autosave, build) and root views.
- `CardStock/Site`: the site engine, no UI. Front matter parser, template engine, `Site` loader, `SiteRenderer` (used by both build and preview), `SiteBuilder` (writes `public/`).
- `CardStock/Editor`: item editor (`MarkdownEditor` is an NSTextView so images can be dropped/pasted at a position and inserted at the cursor; `MarkdownStyler` restyles the text on every edit (look only, text stays plain Markdown); the formatting bar's edits come from `MarkdownFormatting`, pure string logic covered by `FormattingTests`; `InsertImageSheet` + `Site/ImageImporter` scale images with ImageIO; `Site/Lightbox` injects the lightbox into pages) and the live preview (a WKWebView serving the in-memory site over the `cardstock-preview://` scheme).
- `CardStock/Files`: Files page listing everything in `media/` (`Site/MediaLibrary`: scan, pairs `-small` versions, usage, Markdown, add, move to the Mac's Trash). `Site/FolderWatcher` (FSEvents) on the site folder refreshes it when Finder changes files. `Site/LocalData` owns `.cardstock-local/` (per-Mac, gitignored).
- `CardStock/Help`: Help Center. Articles are Markdown files in `Resources/Help` (front matter: title, category, summary, order), bundled as a folder reference. The list shows in the center column, the article in the right column. Link articles with `help:<file name>` and app sections with `cardstock:<configuration|status|publishing|files|pages|home>` or a Configuration page (`ConfigPage.linkName`: site-details, collections, folders, tags, templates, layouts, fonts, colors, top-bar, footer, components, newsletter, search); `HelpTests` checks every link.
- Site icon: `SiteConfig.Icon` (`icon` in site.json: image, background, home screen name, optional custom favicon), edited in Site Details (`Settings/SiteIconSection`, with a preview drawn by the same code). `Site/SiteIcon` renders the PNG sizes (apple-touch 180, Android 192/512, maskable 512, favicon 32) with AppKit drawing and writes `site.webmanifest` from `SiteBuilder`; `SiteIcon.headHTML` adds the tags in `SiteRenderer.wrap`. `SiteIconTests`.
- `CardStock/Start`: Start screen shown when a site opens (preview hidden): tiles for common tasks plus a dashboard (`DashboardViews`: activity calendar from `git log` dates, writing stats with a Swift Charts bar chart). `StatusView` (Status, under Start in the sidebar, `SidebarSelection.status`) has the How CardStock Works diagram at the top (`HowItWorksCard`: Mac and other computers, GitHub, Cloudflare Pages, domain, each with its set-up state), then the health checklist (`HealthCard`) and `ActivityLogCard` side by side at a fixed height, each scrolling inside (the log is over `App/ActivityLog`: one app-wide JSON Lines file in Application Support, newest 5000 entries, each tagged with its site's folder; `AppModel.log`/`logEdit` (continuous edits at most every 10 minutes) are called from the model's actions, every `errorMessage` is logged, and `checkHostingBuild` logs the host's build of the latest commit once each, from `GitHubClient.buildChecks` (check runs and commit statuses), after a publish, on open and with each GitHub check; filters, search, export, delete; `ActivityLogTests`), `StorageCard` (repository and file sizes against GitHub's and Cloudflare's limits) and help articles for fixing problems; its sidebar badge is `AppModel.healthProblemCount`, recounted shortly after `revision`, `files` or `outdatedThemeFiles` change. The numbers and checks come from `Site/SiteInsights` (tested in `InsightsTests`). Chart colors are one blue ramp validated for light and dark.
- Page types: every page is a Markdown file in `pages/`; `ContentKind` (`Site/ContentCollection.swift`, from `type:` front matter, `ContentItem.kind`) is `.page`, `.links`, or a collection's `.main(id)` (`pages/<id>.md` with `type: collection`), `.item(id)` (`type: <id>`, or `post`/`product` for the blog and shop) and `.category(id)` (`type: <id>-category`). `.post`, `.product`, `.blogCategory`, `.shopCategory` are shorthands. Paths come from the kind alone (`ContentKind.path(for:)`): only collections have their own address (main `/<id>/`); items and categories are `/<id>/pages/<slug>/`, every other page `/pages/<slug>/` (Search: `ContentItem.searchPath`), Home `/`. There's no address setting in the UI. Sites from before 0.6 (`SiteConfig.addressVersion` 1) are moved once on open by `SiteMigration.moveAddresses` (rewrites internal links in pages, top bar and footer; adds `static/_redirects` lines from `ContentKind.legacyPath`). Names, icons and summaries come from the config (`SiteConfig.singularName/pluralName/systemImage/summary`, `kinds` for menus; `PageKindOptions` builds Type menus). `Site/SiteMigration` moves old `posts/` and `projects/` folders into `pages/` when a site opens. Themes missing the newer templates fall back to the bundled ones (`SiteRenderer.newerTemplateNames`: collection, item, tags).
- Collections: `ContentCollection` (`collections` in site.json; `SiteConfig.storedCollections` is nil for older sites and `Site.load` fills in `ContentCollection.defaults`: blog, plus shop when there are products) with a `Preset` (blog, shop, portfolio, videos, custom) and settings for the main/category list (`listStyle` list/cards/gallery, columns, sort, shown fields, category links), item pages (dated, cover, tags, categories, selling, video, prevNext, itemLayout) and elsewhere (categories, onHome, inFeed). Edited in Configuration → Collections (`Settings/CollectionsView`, `AddCollectionSheet`, which the page editor's Type menu also opens (`PageKindOptions.newCollection`) to make that page the new collection's main page: `addCollection(_:mainPage:)` moves the file to `pages/<id>.md`, updates links, adds a redirect and removes older ones away from the new address; `SiteBuilder` also drops `static/_redirects` lines whose source is a published page, which would hide it or loop (`SiteMigration.redirects(_:keepingPages:)`, `RedirectTests`); `AppModel.addCollection/removeCollection/openMainPage`, `configCollectionID` picks the one shown and previewed). The renderer's `collection.html` gets `listing`/`categoryNav` HTML (`listingHTML`, `categoryNavHTML`), `item.html` gets `item.meta/actions/videoEmbed/pager`; `collectionStyle` CSS is injected into pages that use those classes. Main pages without a file still render once there are items (`allCollections` includes stand-ins for collections pages name but site.json lacks; health check flags them). Home lists `homeItems` (onHome collections); the feed uses inFeed collections. `CollectionTests`.
- Folders: Configuration → Folders (`Settings/FoldersView`, `NewFolderSheet`) lists `SiteConfig.systemFolders` (one per collection, plus pages, tags, media, assets; locked) and your own `folders` (`Folder`: name → page slug, or a collection id for its main page), short addresses that render the page as at its own path (`SiteRenderer.folderTarget`; `paths` adds them). `SiteConfig.folderProblem` checks names; collections can't take a folder's name. `FolderTests`.
- Tags: `tags:` front matter on every page (`ContentItem.tags`; tag pages list only `isListedOnTagPages` ones), edited with `Editor/TagEditor` (chips, suggestions). Files in media/ are tagged in `media.json` (`MediaTags`, `Site.mediaTags`, `MediaFile.tags`; `FileTagEditor` in the Files preview, several files at once; `AppModel.updateFileTags/changeTags`; saved right away, reloaded in `refreshFiles`); tag pages show tagged photos as a gallery and other files as links. `Site.tagIndex()` merges spellings by `TagSettings.slug`; `TagSettings` (`tags` in site.json: `pages` on/off, `list` of tags with descriptions). Tag pages `/tags/` and `/tags/<slug>/` render with `tags.html`. Configuration → Tags (`Settings/TagsView`): rename/merge/delete across pages (`AppModel.renameTag/deleteTag`, logic in `ContentItem.tags(renaming:to:)` and `TagSettings.rename`), descriptions, preview (`previewTagSlug`).
- Page layouts: `Site/PageLayout` reads `theme/layouts/*.html` (a leading comment gives name, description, areas, main area, types) into `Site.layouts`; a page picks one with `layout:` front matter (`ContentItem.layout`, `EditorView`'s `LayoutPicker`). `<!-- section -->` lines split the Markdown into sections that fill the layout's areas (`PageLayout.sections`, `areaText`). `SiteRenderer.renderLayout` adds `section.N`, `page.sections/meta/actions/listing`, `recentPosts`, `blogCategories`. Configuration → Layout (`Settings/LayoutsView`) starts with page-wide settings (content width from `ThemeSettings.popularContentWidths` or custom, default 960 px; side padding `gutter`; the top bar's and footer's own widths, `fullWidthHeader`/`fullWidthFooter`, are on their pages), then lists them and previews a sample at `/_layouts/<id>/` (never published). Missing layouts fall back to Standard and show in the health checks.
- Newsletter: `SiteConfig.Newsletter` (`newsletter` in site.json: heading, text, the service's embed code, card/plain, left/center), edited in Configuration → Mailing List (`Settings/NewsletterSection`; "newsletter" in code, links and the `<!-- newsletter -->` line). A `<!-- newsletter -->` line in a page (editor: envelope button, `MarkdownEditor.newsletter`) is turned into a placeholder by `Newsletter.markPlaces` (skipping code blocks) before Markdown formatting, then `SiteRenderer.insertNewsletter` swaps in the box in `wrap`. No embed code: nothing published, a note in the preview, a health check. Preview sample at `/_newsletter/`.
- Search: `SiteConfig.Search` (`search` in site.json: on/off, which page types, field and button text), Configuration → Search (`Settings/SearchSection`). The Search page is `pages/search.md` (`ContentItem.isSearchPage`, fixed like Home; `Site.ensureSearchPage` adds it and `theme/search.html` on open), rendered with the `search` template, whose inline script loads `/search.json` (`SiteRenderer.searchIndexJSON`, plain text via `plainText`) and filters as you type. `<!-- search -->` lines show a search box (`searchBoxHTML`, editor: magnifying glass). Box lines are handled by `Site/PageWidget` (`markPlaces` before Markdown formatting, `insertWidgets` in `wrap`), shared with the newsletter box.
- Videos in pages: `Site/VideoEmbed` turns a line with a YouTube/Vimeo link or `<iframe>` embed into `SiteRenderer.videoEmbedHTML` (in `markdownToHTML`). YouTube won't play in the preview (no web address: Error 153), so `PreviewSchemeHandler` swaps those players for thumbnails linking to YouTube (`VideoEmbed.previewPlaceholders`); the preview lets https subframes load. `VideoEmbedTests`.
- `Site/LinkMenu`: link menu pages (`type: links` front matter), read for their links and shown as footer drop-down menus (`footer.menus` in site.json); not published at their own address (`SiteRenderer.paths` skips them).
- `CardStock/Pages`: Pages view (every page of every type, filterable by type), four columns with the sidebar: a narrow page list (search/filter/sort), `EditorView` for the selected page (footer has Move to Trash; Home and 404 can't be deleted), and the preview. Opening a page from anywhere (`selection = .item`) goes to this view (`AppModel.selection` didSet).
- `CardStock/Publishing`: optional GitHub link. `Git` runs /usr/bin/git (token passed per run via `GIT_CONFIG_*` env, never written to disk), `GitHubClient` (REST), `Keychain` (one token per GitHub login, per Mac; the old single `personal-access-token` entry is migrated on launch), `GitHubAccounts` (which account a site uses: the one chosen in `.cardstock-local/github-account`, else the repo owner's, else the default; accounts are managed in Settings → GitHub), `ProjectSettings` (the site's `<Name>.cardstock` project file, which also makes the site double-clickable; legacy `cardstock.json` is migrated), `Publisher` (link/publish/pull-rebase logic; a linked folder with no `.git`, e.g. a ZIP download, is reconnected to GitHub's history on publish), `SiteDownloader` (Open from GitHub: `git clone` into a new folder, used by `Publish/OpenFromGitHubSheet`).
- `CardStock/Publish`: Publish page (status card with the main Publish/Build button, Schedule Publish (`SchedulePublishSheet`, `ScheduledPublishCard`; `Publishing/PublishSchedule` saves it in `.cardstock-local/`, `AppModel.armSchedule` waits for it), sync details from `SyncStatus`/`BuildState` (`AppModel.checkGitHubForUpdates` fetches on app activation and every 5 minutes; updates from other Macs show as a purple `UpdateSeal` on the sidebar and `IncomingUpdatesBanner` on the page, which can `useGitHubVersion` for files changed on both sides), how-it-works, GitHub setup, Cloudflare hosting help).
- `CardStock/Settings`: the Configuration view (`ConfigurationView`): a 260-wide list of `ConfigPage`s, the selected one on the right. Site Details (`SiteDetailsView`: site, site icon) comes first, then Collections and Tags, then the look pages from `ThemingView(page:)`: Templates, Fonts, Colors and Components (`ComponentsSection`: corners, buttons, cards, images, code, quotes, tables, menus; `ThemeSettings` → `theme/theme.json`, injected as CSS variables into every page head and read by style.css), Top Navigation Bar (`TopBarSection`, saved as `header` in site.json: style, logo (`LogoImageRows`, shared with the footer) with left/center/right position and padding, optional dark versions of the logo and compact logo (`darkLogo`/`darkCompactLogo`: used outright on always-dark sites, swapped in with a `<picture>` by `SiteRenderer.insertDarkLogos` on Auto ones, so older themes get them too), three `LinkGroupSection`s, left, center and right (`nav`), each with a switch (links stay listed when off), Link Style (font, size, weight: `ThemeSettings.navFont/navSize/navWeight`, so Google fonts load and Templates carry them) Link Colors (`navLight`/`navDark` `NavColors`, empty follows the palette) and Button Style (`ThemeSettings.navButton`); the bar's background (page color, custom light/dark color with opacity, or none), blur and bottom line with its own color, thickness and style, kept while it's off, and the phone menu button's icon, color and size (`Site/MenuButton`: `header.menuButton`, `menuButtonStyle`, `insertMenuIcon` swaps the button's SVG so older themes get it too, and `insertCloseButtonScript` moves the overlay's ✕ onto the button's spot when it opens) (`header.bar`, `SiteRenderer.headerBarStyle` adds a `<style>` only when they differ from the theme's; `HeaderBarTests`); on phones the links fold into a menu button and a full-screen overlay (`header.mobileMenu`, markup and script in base.html); each top bar `NavLink` can be a `button` and have an `icon` (`NavIconMenu` on its `LinkRow`), from `Site/NavIcons` (bundled Lucide SVGs, ISC; `symbol` is an SF Symbol look-alike for menus); `SiteConfig.menuLinks` is every shown link; `SiteRenderer.headerValue` feeds base.html's three `.bar-slot`s, and a small script in base.html shrinks the bar by setting `--p`) and Footer (`FooterSection`, saved as `footer` in site.json). `AppModel.showConfiguration(_:)` opens a page. The toolbar Preview button slides in a fourth column (`showConfigPreview`, off by default) showing the Template page: `pages/template.md` (`ContentItem.isTemplatePage`, fixed like Home and 404, listed in Pages) rendered with `theme/template.html`, every component of the style on one page, at `SiteRenderer.templatePagePath` (`/_template/`) for the preview only (not in `paths`, never published). Sites without it get both files on open (`Site.ensureTemplatePage`); a missing template falls back to the bundled one. The saved looks (`StyleLibrary`) are called Templates in the UI. Configuration → Templates (`Settings/StylesSection`) is a gallery of cards, each a `TemplatePreview` drawn from the settings (web fonts shown as the closest Mac design): CardStock Default, the six `Site/BuiltInTemplates` (`AppModel.StyleChoice.builtIn`, `applyBuiltInTemplate`; `BuiltInTemplateTests`), then My Templates (unsaved look and saved ones, with a context menu).
- `CardStock/Resources/StarterSite`: the site that "New Site" copies, including the default theme. Bundled as a folder reference.
- `CardStock/Resources`: asset catalog (accent color) and `AppIcon.icon`, the app icon made in Icon Composer. Edit it with Icon Composer; Xcode compiles it into AppIcon.icns, which the `.cardstock` and `.cardstockstyle` document types also use (`CFBundleTypeIconFile`/`UTTypeIconFile` in `project.yml`).
- `CardStock/Info.plist` is generated by XcodeGen from the `info:` block in `project.yml` (document types for `.cardstock` and `.cardstockstyle`). Edit `project.yml`, not the plist. Finder opens arrive via `AppDelegate.application(_:open:)`, which owns the `AppModel`.
- The app is not sandboxed (it needs to run git and edit arbitrary folders); hardened runtime is on.

## Site format
- Defined in `docs/site-format.md`. Keep that spec in sync with the engine when either changes.
- CardStock renders the site into `public/` and commits it. Cloudflare Pages has no build command; output directory is `public`.
- Markdown is rendered with swift-markdown's `HTMLFormatter`.
- Styles (`StyleLibrary`, saved looks) are app-wide, stored in ~/Library/Application Support/CardStock/Styles, and exported as `.cardstockstyle` JSON (old `.cardstocktheme` files still import). Using a style copies it into the site's `theme/theme.json`; sites never depend on the library.
- GitHub is optional; sites must keep working fully without it. Sign-in is a personal access token for now (a registered GitHub app may come later).

## Gotchas
- The project lives on an exFAT external drive. `hdiutil` can't write images there, so `make-dmg.sh` builds the DMG in a temp dir and copies it into `dist/`.
